## 1. Зачем

Модель архитектуры хранится в YAML в git, и сейчас её можно менять только руками. Команды должны **сами заводить и менять свои продукты и сервисы** через UI, а результат должен попадать в **корпоративный GitLab как MR**. Дальше идёт обычный процесс: CI с проверками и ревью архитектора.

Редактор ничего не хранит сам. Он читает модель из репозитория, помогает корректно заполнить YAML и создаёт MR. Источником правды остаётся git.

## 2. Цели, не-цели, анти-цели

**Цели**
- Мастер по шагам для нового сервиса, нового продукта и новой команды (вариант B, выбран пользователем).
- Изменение существующего сервиса или продукта: тот же мастер, заполненный текущими значениями, по шагам можно переходить свободно.
- Удаление сервиса через MR.
- Ссылки на другие элементы модели (сегмент, кластер, сервер СУБД, ресурс, топик, вызываемый сервис, сущность, внешняя система) выбираются из списков, построенных по текущей модели. Сослаться на несуществующее нельзя.
- Имена по регламенту (namespace, ТУЗ, Vault, схема БД, бакет, топики) показываются сразу при вводе.
- Проверки (схема + правила A-1, A-2, цепочки, WAF, ответственные) выполняются в браузере тем же кодом, что в CLI. Ошибки показываются на шаге, к которому относятся, и сводно на последнем шаге.
- Последний шаг «Проверка и MR»: предпросмотр пяти разрезов для изменяемого продукта с учётом изменений, список проверок, diff изменённых YAML, создание MR.
- MR создаётся от имени пользователя, его правами в GitLab.

**Не-цели**
- Редактирование `_shared` (сегменты, кластеры, ресурсы, серверы СУБД, источники трафика). Решение пользователя: это делают архитекторы обычным MR. В редакторе `_shared` только читается.
- Согласование, комментарии и мерж внутри редактора. Всё это делается в GitLab.
- Собственный сервер, база данных или хранилище черновиков на сервере.
- Редактирование произвольного YAML текстом.
- Переименование продукта или сервиса. Имя неизменно по регламенту 2.1, переименование идёт через архитектурный комитет.
- Удаление продукта или команды. Делается вручную, это редкое и рискованное действие.

**Анти-цели (провал, даже если «работает»)**
- MR, который не проходит CI-проверку `arch:validate`, хотя редактор показал «ошибок нет». Проверки в редакторе и в CLI должны давать одинаковый результат.
- Потеря ручного форматирования и комментариев в YAML при изменении существующего файла: diff должен содержать только реальные изменения.
- Тихая перезапись чужих изменений. Если файл в `main` изменился после того, как редактор его прочитал, пользователь должен об этом узнать.
- Токен GitLab с правами шире, чем нужно, или хранение токена дольше сессии.

## 3. Ограничения

- Корпоративный GitLab (решение пользователя). Нужно OAuth-приложение с PKCE (GitLab ≥ 13.x), redirect URI — адрес редактора на GitLab Pages, scope `api` (создание веток, коммитов и MR; более узкого scope для записи в GitLab нет).
- Статическая страница без сервера (подход 1, выбран пользователем). Все вызовы идут из браузера в GitLab API.
- Используется тот же код, что в `_tool`: схемы (`schemas.ts`), разрешение модели (`resolve.ts`), проверки (`checks/**`), разрезы (`views/**`), имена (`names.ts`, список запрещённых слов — `checks/naming.ts`). Проверено: Node-модули импортируют только `load.ts` (файловая система) и `resolve.ts` (`node:path` для путей `_shared` — заменить на склейку строк, решение Claude); остальное уже работает в браузере.
- **Равенство с CI** (решение Claude): CI запускает `arch:validate` по всему репозиторию — схемы, разрешение, `runChecks`. Редактор выполняет тот же конвейер по всему дереву файлов в памяти (включая `_shared`) с наложенной корзиной. Других проверок в CI нет, поэтому результаты совпадают по построению; §9 закрепляет это тестом.
- Регламент разработки: формулы имён (раздел 2), ветки и MR (раздел 4).
- Масштаб — сотни сервисов: загрузка всей модели при открытии должна укладываться в несколько секунд.

- **Права команд** (ответ пользователя): у команд роль Developer в репозитории модели, они могут создавать ветки. MR создаётся из ветки в том же проекте, форки не нужны. Рекомендация (решение Claude): защитить `main` — мерж только через MR с одобрением по `CODEOWNERS`.
- **Неизвестно** (ответ пользователя): можно ли в корпоративном GitLab завести public OAuth-приложение с PKCE и scope `api`, разрешён ли CORS к `/oauth/token` и `/api/v4` с домена Pages, закрыт ли Pages авторизацией. Поэтому **первая задача плана — проверка на реальном GitLab** (§11). Если проверка не проходит, основным режимом становится запасной (zip), а интеграция откладывается до решения админов.

## 4. Рассмотренные подходы

| # | Подход | Плюсы | Минусы |
|---|---|---|---|
| 1 | **Статическая страница на GitLab Pages, OAuth PKCE, всё в браузере через GitLab API** | Нет своего сервера и базы. Права и аудит в GitLab, автор MR — сам пользователь. Развёртывание тем же CI. | Админы GitLab должны зарегистрировать OAuth-приложение. Нужен GitLab ≥ 13. |
| 2 | Небольшой сервер с сервисной учётной записью | Можно добавить серверную логику: черновики, уведомления | Отдельный сервис и ТУЗ с правами на репозиторий. Автор MR — бот. |
| 3 | Без интеграции: мастер выдаёт архив YAML и инструкцию | Работает сразу и где угодно | Ручной шаг, команды будут ошибаться с путями и ветками |

**Выбрано: подход 1** (решение пользователя). **Решение Claude:** подход 3 встраивается как запасной режим. Если OAuth не настроен (нет конфигурации или для пилота без GitLab), кнопка «Создать MR» становится «Скачать изменения»: zip с изменёнными файлами по их путям плюс текст описания MR. Модель в этом режиме загружается из файла `model.json`, который CLI кладёт рядом при сборке (см. §7.2).

## 5. Пользовательский сценарий

1. Пользователь открывает редактор (адрес на GitLab Pages) и нажимает «Войти через GitLab».
2. Редактор загружает модель из `main` (см. §7.1). Слева дерево команд, продуктов и сервисов, как в просмотрщике. Кнопки: «+ сервис» в продукте, «+ продукт» в команде, «+ команда».
3. Выбор существующего сервиса открывает мастер с заполненными значениями. Шаги можно открывать в любом порядке.
4. Мастер сервиса, шаги:
   1. **Основное**: имя (`name`), тип (backend/ui/worker/job/gw), критичность. Сразу виден id и все выведенные имена. Имя проверяется регуляркой и списком запрещённых слов, у существующего сервиса не редактируется.
   2. **Размещение**: сегмент и кластер (списки из `_shared`), порт и протокол.
   3. **Данные**: свои БД (сервер СУБД из списка, классификация), публикуемые события (сущность из каталога продукта, событие, версия, брокер). Тут же отображаются выводимые имена схемы, пользователей и топиков.
   4. **Связи**: синхронные вызовы (сервис или внешняя система из списка, протокол, сущности), читаемые топики (список всех топиков модели), используемые ресурсы (ресурс из списка; для S3 — назначение или полное имя бакета и доступ; сущности, назначение), подключения к БД (`db` + роль), выгрузки (CDC/batch, цель, сущности).
   5. **Публикация**: для кого (`audience`: акторы из `_shared`) и цепочка входа (`via`: ресурсы, по умолчанию WAF → Ingress для интернета). Без WAF для интернета показывается ошибка правила.
   6. **Ответственные и ссылки**: список `owners` (роль, имя, контакт) и `links` (вид, URL, название). Если ответственных нет, показывается предупреждение и подсказка, что будут унаследованы ответственные продукта.
   7. **Проверка и MR**: сводка проверок по всей модели с изменениями (ошибки блокируют кнопку MR, предупреждения нет), предпросмотр пяти разрезов в охвате продукта (компонент просмотрщика), diff каждого изменённого файла, заголовок и описание MR (заполнены автоматически, можно править), кнопка «Создать MR».
5. Мастер продукта: Основное (код — из реестра систем, проверка регуляркой, у существующего не меняется; название; критичность; НФТ), Сущности (каталог: имя, классификация, сервис-владелец), Выделенные ресурсы (внешние системы продукта; серверы СУБД и ресурсы продукта только для просмотра, если они заданы), Ответственные и ссылки, Проверка и MR.
6. Мастер команды: название, ответственные, ссылки, Проверка и MR. Id команды (имя папки) задаётся при создании, латиница по тем же правилам.
7. В одном MR может быть несколько изменений. Пока MR не создан, правки копятся в «корзине изменений» (счётчик в шапке). Пример: новый продукт, два его сервиса и новая сущность. Последний шаг показывает все изменённые файлы.
8. После создания MR показывается ссылка на него, корзина очищается. Повторное открытие показывает модель из `main` (MR ещё не смержен), поэтому вверху виден баннер со ссылками на открытые MR пользователя с меткой `arch-editor`.

## 6. Как изменения превращаются в файлы

- Пути файлов — по структуре модели: `<team>/team.yaml`, `<team>/<code>/product.yaml`, `<team>/<code>/services/<name>[-<type>].yaml`. Имя файла сервиса — `name` плюс суффикс типа, как в демо.
- **Новый файл** генерируется в каноническом порядке полей, как в демо-модели, без пустых необязательных полей.
- **Изменение существующего файла** выполняется через `yaml` Document API на исходном тексте: меняются только затронутые узлы, комментарии, порядок ключей и стиль (flow/block) остальных узлов сохраняются. В diff попадают только реальные изменения.
- Удаление сервиса удаляет его файл. Если на сервис ссылаются другие (вызовы, владельцы сущностей), проверка покажет ошибки ссылок, и MR не создастся, пока ссылки не убраны в той же корзине.
- Перед показом diff и проверок изменения накладываются на загруженное дерево файлов в памяти. Дальше работает тот же конвейер, что в CLI: разбор, схема, разрешение, проверки.

## 7. Технические решения

### 7.1. Загрузка модели из GitLab
- `GET /projects/:id/repository/tree?ref=main&recursive=true&per_page=100` (с пагинацией) даёт список `*.yaml` вне каталогов на `_` (кроме `_shared`). Для каждого файла `GET /projects/:id/repository/files/:path/raw?ref=<sha>` с ограничением параллельности (по умолчанию 8). Одновременно запоминается `sha` коммита `main`, на котором прочитана модель (`base_sha`).
- Если тот же `base_sha` уже прочитан в этой вкладке, используется кэш в `sessionStorage`.
- `last_commit_id` файла (нужен для `update`/`delete`, §7.3) запрашивается лениво — только для изменяемых и удаляемых файлов, при переходе на шаг «Проверка и MR»: `HEAD /projects/:id/repository/files/:path?ref=main`, заголовок `X-Gitlab-Last-Commit-Id` (решение Claude).

### 7.2. Загрузчик без файловой системы
- Из `load.ts` выделяется чистая функция `loadTreeFromFiles(files: Record<string, string>): { tree, errors }` без Node-модулей. Её используют и CLI (обёртка читает файлы с диска), и редактор. Поведение CLI не меняется, это подтверждается существующими тестами.
- CLI при `build` дополнительно пишет `_dist/model.json` (`{ files: Record<путь, текст>, builtAt }`) для запасного режима без GitLab.

### 7.3. Создание MR
- Ветка `arch/<краткое описание латиницей>-<короткий случайный суффикс>` (например `arch/crm-notify-worker-3fk2`).
- Один вызов `POST /projects/:id/repository/commits` с `branch`, `start_sha = base_sha`, `actions[]` (`create`/`update`/`delete`). Для `update` и `delete` передаётся `last_commit_id`, последний коммит файла на момент чтения. Если файл с тех пор изменился, GitLab отклонит коммит, и редактор покажет сообщение «файл изменён в main после загрузки — обновите модель», без перезаписи.
- `POST /projects/:id/merge_requests`: `source_branch`, `target_branch = main`, `title`, `description` (сгенерированный список изменений и итог проверок), `labels: arch-editor`, `remove_source_branch: true`. Ревьюеры назначаются через `CODEOWNERS` в репозитории (см. §8), редактор их не выбирает.
- Сообщение коммита: `arch: <заголовок MR>`.

### 7.4. Авторизация
- OAuth 2.0 Authorization Code + PKCE в браузере. Токен хранится только в памяти вкладки (не в localStorage), при перезагрузке нужен повторный вход (GitLab с активной сессией пропускает его без ввода пароля). Refresh-токен не сохраняется.
- Конфигурация в `config.json` рядом с редактором: `gitlabUrl`, `projectPath`, `oauthClientId`, `redirectUri`, `baseBranch` (`main`). Если `oauthClientId` пустой, включается запасной режим (§4).

### 7.5. Черновики
- Корзина изменений автоматически сохраняется в `localStorage` (ключ по проекту), чтобы закрытая вкладка не теряла работу. Корзина хранится пофайлово: путь, новое содержимое (или удаление) и `blob_id` исходного файла на момент правки (решение Claude).
- При открытии с более новым `main`: файлы, чей `blob_id` в `main` не изменился, применяются молча; изменённые в `main` помечаются конфликтом с двумя действиями — «отбросить мою правку этого файла» или «открыть в мастере заново» (мастер заполняется уже из нового `main`, правка повторяется вручную). Автослияния нет.

### 7.6. Код и сборка
- Новый каталог `_tool/editor/` (рядом с `viewer/`) на том же стеке: TypeScript без фреймворка, esbuild. Предпросмотр переиспользует код отрисовки из `viewer/` (компонент графа и панели).
- Команда `npm run editor:build` собирает `_dist/editor/` (`index.html` + бандл + `config.json` из переменных CI). Пример задания GitLab CI публикует его на Pages.
- Мастер — модуль форм со схемой шагов на основе тех же JSON Schema и списков из модели; общий код форм для сервиса, продукта и команды.
- **Поля вне мастера** (решение Claude): `overrides` сервиса, `dbservers`/`resources` продукта и любые поля, которых нет в шагах, при изменении существующего файла сохраняются как есть и показываются на соответствующем шаге только для чтения с пометкой «меняется вручную в YAML». Мастер их не удаляет и не создаёт.
- **Запасной режим** (решение Claude): `model.json` содержит `{ files, builtAt, commit? }` (`commit` — SHA из `CI_COMMIT_SHA`, если есть). Zip содержит только изменённые файлы по их путям и `MR.md` с описанием; обнаружения конфликтов нет, в интерфейсе показана дата сборки модели.

## 8. Изменения в репозитории модели

- `CODEOWNERS` (решение Claude, предложено ранее): `/_shared/` — архитекторы; `/<team>/` — архитекторы и владелец команды. Файл создаётся по шаблону в README, реальные группы GitLab подставляет пользователь.
- Пример задания CI для Pages и описание регистрации OAuth-приложения (что сказать админам: redirect URI, scope `api`, confidential = false) — в `_tool/README.md`.

## 9. Проверки и тестирование

- Модульные тесты: `loadTreeFromFiles` (те же кейсы, что `loadTree`), генерация нового YAML по каждому виду файла, минимальный diff при изменении существующего файла с комментариями, наложение корзины на дерево, построение `actions[]` для коммита, имя ветки.
- Тесты мастера: значения списков (сегменты, кластеры, топики…), блокировка MR при ошибках, отображение ошибки правила на нужном шаге.
- e2e в Chrome (puppeteer-core, как у просмотрщика) с **локальным фальшивым GitLab API** (мини-сервер в тестах, отдаёт демо-модель и принимает commits/MR). Сценарии: вход (фальшивый OAuth), новый сервис → MR; изменение существующего → минимальный diff; конфликт `last_commit_id` → сообщение; запасной режим → скачивание zip.
- Равенство с CLI: для набора изменений результат проверок в редакторе совпадает с `arch-views validate` по тем же файлам.

## 10. Что остаётся строителю

- Внешний вид шагов, валидация полей на лету, тексты подсказок — в стиле просмотрщика (те же CSS-токены, светлая и тёмная темы).
- Структура модулей внутри `editor/`, генерация описания MR.
- Ограничение параллельности и пагинация GitLab API, тексты ошибок сети.
- Упаковка zip в браузере для запасного режима (без внешних CDN, библиотека в бандле).

## 11. Первая задача: проверка на реальном GitLab

Цель — до основной разработки убедиться, что подход 1 работает в вашем GitLab. Это одноразовая минимальная страница (не часть редактора), которая:
1. Читает `config.json` (`gitlabUrl`, `projectPath`, `oauthClientId`, `redirectUri`).
2. Выполняет вход OAuth + PKCE и показывает имя пользователя (`GET /api/v4/user`).
3. Читает дерево репозитория модели и один файл (`repository/tree`, `files/:path/raw`).
4. По кнопке создаёт ветку `arch/spike-<суффикс>` с одним новым файлом (`repository/commits`) и MR в черновом статусе (`Draft:`), выводит ссылку.
5. На каждом шаге показывает понятный результат: «успешно» или текст ошибки (CORS, 401/403, неверный redirect).

Для проверки пользователь просит админов GitLab зарегистрировать OAuth-приложение (redirect URI — адрес страницы на Pages или `http://localhost:<порт>/` для локального запуска, scope `api`, confidential = false).
