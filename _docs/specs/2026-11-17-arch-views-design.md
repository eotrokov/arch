# Система архитектурных схем по разрезам — дизайн

| Параметр | Значение |
|---|---|
| Дата | 2026-11-17 |
| Статус | Черновик на согласование |
| Связанные документы | `docs/development-regulations.md` (разделы 2, 12) |

## 1. Зачем

Архитектору на согласовании сервиса/продукта нужно увидеть одну и ту же систему в разных разрезах: Kubernetes, контейнеры, фаервол (сегменты сети и соединения с портами), базы данных, потоки данных. Источник — описание в репозитории («архитектура как код»), а не живая конфигурация.

Ключевое требование: **одна модель — много разрезов**. Каждый элемент описан один раз; разрезы — проекции модели, поэтому не расходятся между собой.

## 2. Цели, не-цели, анти-цели

**Цели**
- Модель в `arch/`, разложенная по дереву команда → продукт → сервис.
- Пять разрезов: Kubernetes, контейнеры (C4 L2), фаервол, БД, потоки данных.
- Выбор охвата: вся компания / команда / продукт / сервис с соседями.
- Проверки соответствия регламенту при сборке (раздел 6).
- Интерактивная статическая HTML-страница + экспорт Mermaid для разрезов «контейнеры» и «фаервол» (видны прямо в MR).

**Не-цели**
- Чтение реальной конфигурации (k8s API, выгрузки правил МСЭ, NetworkPolicy) и сверка с ней.
- Окружения, кроме prod (регламент требует Deployment-описание только для prod). Модель не должна этому мешать в будущем, но в первой версии env = prod.
- Редактирование модели через UI. Модель правится только в YAML.
- Генерация заявок на доступы. Таблица соединений должна быть пригодна для копирования, но формат заявки — не задача этой версии.
- C4 L3 (компоненты внутри сервиса).

**Анти-цели (провал, даже если «работает»)**
- Разрезы противоречат друг другу (порт в фаерволе не совпадает со связью в контейнерах).
- Архитектору приходится вручную писать имена, которые выводятся из регламента — и они расходятся с формулой.
- Описание одного факта в нескольких местах (сервис объявляет связь, и её же надо отдельно прописать в фаерволе).
- Нужен сервер или аккаунт, чтобы посмотреть схему.

## 3. Ограничения

- Регламент, раздел 2: имена выводятся по формуле `<system>-<service>[-<type>]` и сквозной таблице 2.4.
- Регламент, 12.2: диаграммы как код, бинарных картинок без исходника нет. YAML-модель — исходник; Mermaid-экспорт — дополнительно текстовые диаграммы.
- Регламент, 12.1/12.4: правила A-1, A-2, глубина синхронной цепочки ≤ 3, нет циклических синхронных зависимостей.
- Просмотр — без сервера: один HTML-файл, открывается локально и из артефакта CI.

## 4. Рассмотренные подходы

| # | Подход | Плюсы | Минусы |
|---|---|---|---|
| 1 | **Свой CLI + интерактивный просмотрщик** (Cytoscape.js + ELK) | Все пять разрезов как задумано, переходы между разрезами по клику, компаунд-рамки для сегментов/namespace | Больше всего работы, раскладку больших схем надо подстраивать |
| 2 | Генерация D2/Mermaid на каждый разрез×охват + HTML с вкладками | Быстро, Mermaid рендерится в GitLab MR | Статично, нет перехода между разрезами, взрыв числа файлов, Mermaid плохо раскладывает большие схемы |
| 3 | Генерация Structurizr DSL + Structurizr Lite | C4 и раскладка из коробки | Фаервол с портами и потоки с классификацией в C4 не ложатся; два инструмента; нужен сервер |

**Выбрано: подход 1 + экспорт Mermaid** для разрезов «контейнеры» и «фаервол» (решение пользователя). Причина: одна модель с переключаемыми разрезами — центральное требование; подходы 2 и 3 его не держат. Mermaid закрывает «видно прямо в MR».

## 5. Структура модели

### 5.1. Дерево файлов (решено с пользователем)

```
arch/
├── _shared/
│   ├── network.yaml        # сегменты сети, общие соединения (мониторинг, бэкапы, админ-доступ)
│   └── platform.yaml       # общая инфраструктура: кластеры, Kafka, ingress, Vault и т. п.
├── <team>/
│   ├── team.yaml           # команда: имя, владелец, контакты
│   └── <product>/
│       ├── product.yaml    # продукт: код системы, внешние системы, НФТ
│       └── services/
│           └── <service>.yaml
```

### 5.2. Сущности и правила

- **Продукт = система (`system`) из регламента.** Код продукта (каталог `<product>` и поле `code`) — основа всех выведенных имён. Каталог продукта ДОЛЖЕН совпадать с `code`.
- **Команда** — владелец и группировка; в имена не входит.
- **Сервис** описывает только своё:
  - `name` (часть `<service>`), `type` (суффикс из 2.3: *нет*, `ui`, `worker`, `job`, `gw`), `segment`, `criticality`;
  - `cluster` (обязательно, решение пользователя: кластер выбирается для каждого сервиса) — ссылка на кластер из `_shared/platform.yaml`;
  - `databases`: которыми владеет — ссылка на сервер СУБД (`server`), классификация данных; имя схемы выводится (`<system>_<service>`);
  - `publishes`: топики/очереди, которые публикует (сущность, событие, версия, классификация);
  - `consumes`: топики/очереди, которые читает;
  - `calls`: синхронные вызовы — цель (полное имя `<system>-<service>` или внешняя система), протокол, порт, sync=true;
  - `uses`: доступ к ресурсам платформы/внешним системам (порт, протокол, назначение);
  - опционально: явные переопределения выведенных имён (с обязательным полем `reason` — это «отступление от регламента»).
- **Идентификатор сервиса** (решение Claude) — полное имя репозитория `<system>-<service>[-<type>]` (`crm-orders`, `crm-orders-ui`). Оно же используется как имя Deployment/ServiceAccount/Helm-чарта, чтобы `crm-orders` и `crm-orders-ui` в одном продукте не конфликтовали. Цели `calls` указываются этим полным именем.
- **Каталог сущностей** (решение Claude) — в `product.yaml`: `entities` (имя, классификация ПДн/КТ/открытые, сервис-владелец). `publishes`, `calls` и `exports` ссылаются на сущности по имени; классификация потока берётся из каталога.
- **Пакетные выгрузки и CDC** (решение Claude) — отдельный вид связи сервиса `exports`: канал (`cdc` | `batch`), цель, сущности, порт/протокол.
- **Подключения к БД** (решение Claude) — в `uses` с `db: <system>_<service>` и `role: rw|ro|migr`. Свои БД: владелец подключается как `rw` неявно; `migr` — у сервиса или его `-job`, выполняющего миграции. Подключение к БД другого сервиса описывается так же — и ловится как нарушение A-1.
- **Ответственные и ссылки** (решение пользователя: у продуктов и сервисов должны быть ссылки на репозитории, документацию, ответственных и т. д.). У команды, продукта и сервиса есть два необязательных списка:
  - `owners`: `{ role, name, contact }`, где `role` — `owner` (владелец продукта), `techlead`, `architect`, `analyst`, `devops`, `security`, `oncall` или произвольная строка; `contact` — почта, мессенджер или ссылка, показывается как текст;
  - `links`: `{ kind, url, title? }`, где `kind` — `repo`, `docs`, `api` (OpenAPI/AsyncAPI), `adr`, `wiki`, `tracker` (Jira), `dashboard`, `alerts`, `runbook`, `ci`, `other`; `url` — только `http(s)`.
  - Ссылка на репозиторий сервиса выводится автоматически: `<git>/<system>/<repo>`, где `git` — базовый адрес из `platform.yaml` (например `https://gitlab.company.ru`). Явная ссылка `kind: repo` её заменяет.
  - В карточке сервиса показываются его ответственные; если у сервиса их нет, показываются ответственные продукта с пометкой «из продукта», а сборка даёт предупреждение `meta.no-owner`. У продукта без `owner` тоже предупреждение.
- **Ссылки между продуктами** — по полному имени (`pay-billing`). Сборщик проверяет, что цель существует.
- **Серверы СУБД** (решение пользователя: у БД должны быть хосты; адресация — только FQDN, IP не нужны) — `dbservers` в `_shared/platform.yaml` (общие) или в `product.yaml` (выделенные продукту): `id`, `engine` (postgres и т. п.), `version`, `segment`, `port`, `hosts: [{ fqdn, role: primary|replica|arbiter }]`, необязательный `endpoint` (VIP/адрес подключения), `owners`, `links`. Сегмент и порт схемы берутся с её сервера. На одном сервере может быть несколько схем разных сервисов.
- **Ресурсы** (решение пользователя: нужны S3, Яндекс Диск, SMTP, Яндекс Мессенджер; бывают и внутренние, и облачные) — единый каталог `resources` в `_shared/platform.yaml` (или `product.yaml`, если выделен продукту): `id`, `kind`, `name`, `endpoint` (FQDN), `port`, `protocol`, `segment`, `owners`, `links`. Внутренний он или облачный, определяет сегмент: облачные — в сегменте с `external: true`. Виды (`kind`): `kafka`, `ingress`, `waf`, `adfs`, `vault`, `s3`, `smtp`, `yandex-disk`, `yandex-messenger`, `other`; новые виды добавляются в перечень без изменения модели.
- **Использование ресурса** сервисом — в `uses`: `resource`, `purpose`, `entities` (какие данные туда уходят), для `s3` — `bucket` и `access: ro|rw`. Короткое `bucket: files` — свой бакет, имя выводится по регламенту `<system>-<service>-<env>-<purpose>` (`crm-orders-prod-files`); полное имя чужого бакета — нарушение A-1, как чужая БД.
- **Аутентификация через ADFS** (решение пользователя) — ADFS описывается ресурсом `kind: adfs`; сервис ссылается на него в `uses` с `purpose` (например «Вход пользователей (OIDC)», «Проверка токенов (JWKS)»). В карточке сервиса — строка «Аутентификация».
- **Публикация сервиса и WAF** (решение пользователя) — у сервиса необязательный список `exposure: [{ audience: internet|corporate, via: [<resource id>...] }]`, где `via` — цепочка ресурсов на входе по порядку (например `[waf-main, ingress]`). Источник трафика — «актор» из `_shared/network.yaml`: `actors: [{ id, name, segment }]` (в демо — `internet` в сегменте `external` и `office` в сегменте `office`); `audience` указывает на актор с тем же id. Из публикации выводится путь `актор → via[0] → … → сервис` (рёбра вида `expose`, привязанные к сервису), который виден в разрезах «Контейнеры» и «Фаервол» (строки таблицы с портами каждого шага) и в карточке («Публикация»). Путь показывается только в охвате, куда входит сам опубликованный сервис.
- **Внешние системы** объявляются в `product.yaml` (если специфичны) или `_shared/platform.yaml` (если общие), с сегментом (обычно `external`).
- **Сегменты** (`_shared/network.yaml`): id, название, описание, признак чувствительности (например `pdn: true`). Каждый узел модели (сервис, БД, ресурс платформы, внешняя система) указывает сегмент; у БД и ресурсов платформы допускается сегмент по умолчанию из их определения.
- **Порты** назначения берутся из цели: БД → порт её сервера СУБД, Kafka → порт брокеров из `platform.yaml`, сервис → порт его API (поле сервиса `port`, по умолчанию 8080), если в связи порт не указан явно.

### 5.3. Выводимые имена (из таблицы 2.4 регламента)

Для системы `crm`, сервиса `orders`, env `prod`: репозиторий/Deployment/Helm/ServiceAccount `crm-orders`, namespace `crm-prod`, ingress `orders.crm.company.ru`, ТУЗ `svc-crm-orders-prod`, Vault `crm/prod/orders`, схема БД `crm_orders`, пользователи `crm_orders_rw|ro|migr`, топик `crm.orders.<entity>.<event>[.vN]`, consumer group `crm-<service>`. Домен (`company.ru`) и registry — параметры в `_shared/platform.yaml`.

## 6. Проверки при сборке

Сборка падает (ошибка) или предупреждает (warning). Отчёт выводится в консоль и показывается в просмотрщике (панель «Нарушения» + подсветка элементов).

Поведение при ошибках (решение Claude): ошибки схемы и битые ссылки не дают построить модель — HTML не создаётся. Ошибки правил (A-1, A-2, цепочки, циклы) не мешают построению: `build` всё равно выдаёт HTML с подсвеченными нарушениями и завершается с ненулевым кодом, чтобы CI пометил MR. `validate` — только проверки, тот же код возврата.

Глубина синхронной цепочки (решение Claude, трактовка регламента 12.4 «не глубже 3 сервисов»): в цепочке не более 3 внутренних сервисов (2 перехода). Считаются все сервисы компании, включая `-gw`; внешние системы и ресурсы платформы не считаются.

| Проверка | Уровень |
|---|---|
| YAML соответствует JSON Schema | ошибка |
| Имена соответствуют регулярке и формуле регламента; переопределение без `reason` | ошибка |
| Ссылка на несуществующий сервис/топик/ресурс/сегмент/сервер СУБД | ошибка |
| Схема с ПДн на сервере СУБД в сегменте без признака `sensitive` | warning |
| Сервер СУБД без хостов; повтор FQDN между серверами | ошибка |
| A-1: сервис обращается к БД, которой не владеет (сравниваются `system` и имя сервиса без типа, а не строка id) | ошибка |
| A-2: у топика/БД больше одного владельца (публикующего/владеющего сервиса) | ошибка |
| Синхронная цепочка вызовов длиннее 3 сервисов | ошибка |
| Циклическая синхронная зависимость | ошибка |
| Топик читают, но никто не публикует / публикуют, но никто не читает | warning |
| Соединение из `external` или в чувствительный сегмент | подсветка (не ошибка) — внимание ИБ |
| ПДн или КТ уходят в сегмент с `external` (облачный S3, Диск, Мессенджер, внешняя система) | подсветка — внимание ИБ |
| Обращение к чужому бакету S3 | ошибка (A-1) |
| Публикация с `audience: internet`, в `via` которой нет ресурса `kind: waf` | ошибка |
| `audience`, не совпадающий ни с одним актором; ресурс из `via`, которого нет | ошибка |
| Межпродуктовое соединение | подсветка |

## 7. Разрезы

Все разрезы строятся из одной внутренней модели (граф узлов и связей с атрибутами).

- **Kubernetes:** кластер (из поля `cluster` сервиса) → namespace `<system>-prod` → Deployment/CronJob (по типу сервиса), ServiceAccount, Ingress-хосты для опубликованных сервисов (есть `exposure` через ресурс `kind: ingress`), независимо от типа сервиса. Рамки: кластер, namespace. Сервисы одного продукта могут быть в разных кластерах — тогда namespace продукта появляется в каждом из них.
- **Контейнеры (C4 L2):** сервисы, БД, брокеры, внешние системы; связи с протоколом. Рамки: продукт.
- **Фаервол:** рамки — сегменты; узлы внутри своих сегментов; стрелки — соединения `сегмент-источник → сегмент-назначение : порт/протокол`, выведенные из `calls`/`uses`/БД/топиков, плюс явные из `network.yaml`. Под схемой — таблица: источник (узел, сегмент) → назначение (узел, сегмент, хосты назначения) → порт/протокол → основание (из какой связи). Для БД хосты назначения — `endpoint` (если задан) и FQDN всех хостов сервера СУБД, для ресурсов — их `endpoint`, чтобы по таблице можно было оформить заявку. Соединения внутри одного сегмента показываются, но в таблице помечаются как внутрисегментные.
- **БД:** рамка сервера СУБД (подпись: engine, версия, endpoint; список хостов с ролями) → схемы с сервисом-владельцем → пользователи `_rw`/`_ro`/`_migr`; кто подключается под каким пользователем. Чужой доступ — красным (нарушение A-1).
- **Потоки данных:** сущности, направления, канал (API / топик / CDC / пакетная выгрузка / ресурс: S3, почта, Диск, Мессенджер), классификация цветом (ПДн / КТ / открытые). Классификация потока = максимальная классификация переносимых данных.

## 8. Охват

Масштаб (ответ пользователя): **сотни сервисов** на компанию. Этого достаточно для одного HTML-файла с раскладкой в браузере, но схема «всё сразу» нечитаема, поэтому:

- Компания: по умолчанию узлы — продукты (свёрнуты), сгруппированные по командам; продукт раскрывается по клику. Раскладка считается для текущего охвата и разреза при переключении и кэшируется в памяти страницы.
- Команда / продукт: элементы охвата + соседи на один шаг (внешние для охвата узлы показываются приглушённо, свёрнутыми до узла продукта).
- Сервис: сервис + всё, с чем у него есть прямые связи.
- В разрезе фаервола (решение Claude) свёрнутые соседи — один узел на пару (продукт, сегмент), чтобы рамки сегментов оставались верными.

## 9. Инструменты и вывод (выбор подхода 1)

- **CLI на TypeScript (Node.js LTS):** команды `validate` (только проверки) и `build` (проверки + вывод). Запускается локально и в CI.
- **Вывод `build`:**
  - `dist/index.html` — один самодостаточный файл: модель встроена JSON-ом, JS/CSS встроены (нужен офлайн и как артефакт CI без сервера).
  - `dist/mermaid/<scope>/containers.md` и `.../firewall.md` — для каждого продукта и сервиса; в CI можно приложить к MR.
- **Просмотрщик:** Cytoscape.js + раскладка ELK (компаунд-узлы для рамок). Слева — дерево охвата (команда → продукт → сервис), сверху — переключатель разреза, справа — карточка элемента (атрибуты, выведенные имена, участие во всех разрезах со ссылкой «показать в разрезе X»), снизу — таблица соединений (для фаервола) и панель нарушений. Поиск по имени. Состояние (охват, разрез, выбранный элемент) — в URL-хэше, чтобы ссылкой можно было поделиться в согласовании.

## 10. Что остаётся строителю

- Точная JSON Schema и названия полей (в рамках 5.2).
- Структура TypeScript-проекта, сборщик бандла (esbuild/vite), тестовый фреймворк.
- Детали визуального оформления, цвета классификаций (с учётом светлой/тёмной темы), настройка ELK.
- Пример модели: одна команда, два продукта (`crm`, `pay`), 4–5 сервисов, с межпродуктовым вызовом и топиком — для демонстрации и тестов.
- Где лежит сам инструмент: РЕКОМЕНДУЕТСЯ `arch/_tool/` (каталоги с `_` в `arch/` не считаются командами).
