# Архитектура как код

Репозиторий с описанием архитектуры систем компании и инструментом `arch-views`, который строит по нему схемы для согласования.

Архитектура описывается **одной моделью** в YAML: команда → продукт → сервис. Из неё строится HTML-страница, где одну и ту же систему можно посмотреть в пяти разрезах:

| Разрез | Что показывает |
|---|---|
| Kubernetes | кластеры, namespace, Deployment/CronJob, ServiceAccount, Ingress-хосты |
| Контейнеры | сервисы, БД, брокеры, ресурсы и внешние системы со связями (C4 L2) |
| Фаервол | сегменты сети и соединения между ними с портами; таблица соединений с FQDN для заявок |
| БД | серверы СУБД с хостами, схемы, пользователи `_rw`/`_ro`/`_migr` и кто под кем подключается |
| Потоки данных | какие сущности куда уходят (API, Kafka, CDC, S3, почта, Яндекс Диск, Мессенджер) с классификацией ПДн / КТ |

Охват выбирается слева: вся компания, команда, продукт или один сервис с соседями. Клик по элементу открывает карточку: имена по регламенту (namespace, ТУЗ, Vault, схема БД…), ответственные, ссылки на репозиторий, документацию, дашборды.

При сборке модель проверяется по регламенту разработки (раздел 12): обращение к чужой БД или бакету (A-1), один владелец у данных (A-2), синхронная цепочка не длиннее 3 сервисов, нет циклов, публикация в интернет только через WAF, указаны ответственные. Соединения в чувствительные сегменты, наружу и между продуктами помечаются для ИБ.

## Структура репозитория

```
arch/
├── _shared/                 # общее для всей компании (создать)
│   ├── network.yaml         #   сегменты сети, источники трафика, общие соединения
│   └── platform.yaml        #   кластеры, Kafka, Ingress, WAF, ADFS, S3, SMTP, серверы СУБД…
├── <команда>/               # модель (создать): одна папка на команду
│   ├── team.yaml
│   └── <продукт>/           #   папка = код системы по регламенту (crm, pay…)
│       ├── product.yaml
│       └── services/
│           └── <сервис>.yaml
├── _tool/                   # инструмент arch-views (CLI, просмотрщик, тесты, демо-модель)
├── _docs/                   # дизайн и план реализации
├── _prototype/              # одноразовый прототип просмотрщика, не используется
└── _dist/                   # результат сборки (не хранится в git)
```

Папки, имена которых начинаются с `_`, командами не считаются.

## Быстрый старт

Нужен Node.js 22.

Посмотреть на демо-модели:

```bash
cd _tool
npm ci
npm run arch:build -- --root examples/demo --out /tmp/arch-demo
open /tmp/arch-demo/index.html
```

Собрать модель из этого репозитория (результат — `_dist/index.html` и схемы Mermaid в `_dist/mermaid/`):

```bash
cd _tool
npm run arch:build
```

Только проверить модель, ничего не собирая:

```bash
cd _tool
npm run arch:validate
```

Код выхода: `0` — всё чисто, `1` — есть нарушения правил (HTML всё равно собирается, нарушения подсвечены), `2` — ошибка в YAML или ссылка на несуществующий элемент.

## Как описать свою систему

Образец всех полей — демо-модель в [`_tool/examples/demo/`](_tool/examples/demo/), полная таблица полей — в [`_tool/README.md`](_tool/README.md).

1. **Общие файлы** (один раз на компанию). Скопируйте `_tool/examples/demo/_shared/` в `arch/_shared/` и замените сегменты, кластеры, ресурсы и серверы СУБД на реальные.
2. **Команда.** Папка `arch/<команда>/` с `team.yaml`:
   ```yaml
   name: Продажи
   owners: [ { role: owner, name: Иванов И., contact: "@ivanov" } ]
   ```
3. **Продукт.** Папка `arch/<команда>/<код>/` с `product.yaml`. Код — из реестра систем, он же основа всех имён (`crm` → `crm-prod`, `crm_orders`…):
   ```yaml
   code: crm
   name: CRM
   owners: [ { role: owner, name: Петрова А., contact: petrova@company.ru } ]
   links:  [ { kind: docs, url: https://wiki.company.ru/crm } ]
   entities: [ { name: order, classification: pdn, owner: crm-orders } ]
   ```
4. **Сервисы.** По файлу на сервис в `services/`. Сервис описывает только своё: где живёт, чем владеет, кого вызывает и что использует:
   ```yaml
   name: orders
   segment: app
   cluster: k8s-prod-1
   databases: [ { server: pg-crm, classification: pdn } ]
   publishes: [ { entity: order, event: created, version: 1, broker: kafka } ]
   calls:     [ { target: pay-billing, protocol: grpc, entities: [order] } ]
   uses:
     - { resource: s3-main, bucket: files, access: rw, entities: [order] }
     - { resource: adfs, purpose: Проверка токенов (JWKS) }
   owners: [ { role: techlead, name: Кузнецов Д., contact: "@kuznetsov" } ]
   ```

Имена (namespace, ТУЗ, путь в Vault, схема и пользователи БД, топики, бакеты, ссылка на репозиторий) выводятся по регламенту автоматически — вручную их писать не нужно. Отступление от формулы — через `overrides` с обязательным `reason`.

Соединения для фаервола тоже выводятся из связей сервисов; вручную в `network.yaml` описываются только общие (мониторинг, бэкапы, админ-доступ).

## CI

Задание GitLab CI для этого репозитория (здесь `arch/` — корень репозитория, поэтому пути без префикса `arch/`):

```yaml
arch:
  image: node:22
  script: [cd _tool, npm ci, npm run arch:build]
  artifacts: { when: always, paths: [_dist/] }
  rules: [ { changes: ["**/*"], exists: ["_shared/network.yaml"] } ]
```

Задание собирает `_dist/` как артефакт MR и падает, если в модели есть нарушения. Пока в репозитории нет `_shared/network.yaml`, оно не запускается. Если `arch/` лежит внутри другого репозитория, используйте вариант из [`_tool/README.md`](_tool/README.md#gitlab-ci) с префиксом `arch/`. В закрытой сети замените `node:22` на образ из внутреннего registry.

## Редактор

Для тех, кто не правит YAML руками, есть веб-редактор: вход через GitLab, мастер по шагам для команды, продукта и сервиса, те же проверки и разрезы, что в просмотрщике, и отправка изменений одним merge request. Он публикуется на GitLab Pages рядом с просмотрщиком (`npm run editor:build`, просмотрщик — по адресу Pages, редактор — по `…/editor/`); без настроенного OAuth работает в запасном режиме и отдаёт изменения zip-архивом. Кто одобряет MR, задаёт `CODEOWNERS` — образец в [`CODEOWNERS.example`](CODEOWNERS.example). Сборка, задание CI для Pages, регистрация OAuth-приложения — в [`_tool/README.md`](_tool/README.md#редактор).
